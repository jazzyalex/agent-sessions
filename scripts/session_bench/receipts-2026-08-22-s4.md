# Receipt: S4 superseded-share measurements (2026-08-22)

Source: external measurements contributed in
[discussion #54](https://github.com/jazzyalex/agent-sessions/discussions/54)

their live stores. This is a command-plus-reported-values receipt: the

unlike `receipts-2026-08-12-codex-c6c7.md` there are no artifact hashes.
Anyone can rerun the same commands against their own store; the numbers

(13.7 GB / 31 GiB / 50 GB stores in
[anomalyco/opencode#33356](https://github.com/anomalyco/opencode/issues/33356)).

## OpenCode — scored (S4 fail, 95.8%)

Rule: keep the newest snapshot per message (final-state-lossless; surviving
events keep their timestamps, superseded intermediate snapshots lose theirs).

```
python3 scripts/session_bench/measure.py \
  --collapse-newest-per-key "$HOME/.local/share/opencode/opencode.db" \
  --collapse-table event \
  --collapse-key "json_extract(data, '$.properties.info.id')" \
  --collapse-order rowid \
  --collapse-bytes "LENGTH(CAST(data AS BLOB))" \
  --collapse-where "type = 'message.updated.1'"
```

Reported: 17,940 `message.updated.1` rows over 4,639 distinct message ids;
378 MB of event rows, of which keeping the newest per message retains 16 MB
→ `superseded_share_pct: 95.8`. Two measurement caveats a reproducer should
know: (1) use `LENGTH(CAST(data AS BLOB))` as above — bare `length()` on a
TEXT column counts characters, not bytes, and under-counts any non-ASCII
content; the contributor-reported figures did not record which form was
used, so a byte-exact rerun may differ slightly while the shape (far above
the 20% limit) holds. (2) The share's denominator is the filtered
`message.updated.1` rows — the tool now also prints the unfiltered
`table_total_row_bytes` so both denominators are on the record. Transcribed into
`measurements-2026-08-04.json` (`agents.opencode.superseded_share_pct`);
`dates.superseded_share: 2026-08-22` marks this measurement's date — the
manifest's `data_date` stays the corpus baseline date, per the existing
`dates` block convention.

## Codex — NOT scored (S4 not_run)

The measured waste is real but sits in `~/.codex/sqlite/logs_2.sqlite`
(a logs/tracing store): 519 MB file, 470 MB (90.6%) on the freelist,
`auto_vacuum=INCREMENTAL` set but never run
([openai/codex#35823](https://github.com/openai/codex/issues/35823)), plus a
167 MB superseded pre-migration copy at the old store location. Codex's
session store is rollout JSONL — the corpus every other Codex cell is
measured on — so per the gate definition this does not score S4.
For reference, the freelist measurement command is:

```
python3 scripts/session_bench/measure.py --freelist "$HOME/.codex/sqlite/logs_2.sqlite"
```

Note on reproducing the 90.6%: that figure is the contributor's
file-size framing (470 MB freelist / 519 MB file). The shipped tool
deliberately computes the share as `freelist_pages / page_count` from one
connection snapshot (bounded on live WAL stores), and reports the store's
`auto_vacuum` mode — so a rerun prints a slightly different, more
defensible number alongside the raw page counts. Both framings agree the
store is overwhelmingly freelist.

## Grok — rule disqualified

"Keep the last event per tool call" is not final-state-lossless for the
source: the prefix property holds for only 66% of tool-call groups (one
8,359-event, 256 MB group carried genuine deltas from a render log), so any
collapse there is a per-file audit, not a format property. Written into the
S4 gate definition.
