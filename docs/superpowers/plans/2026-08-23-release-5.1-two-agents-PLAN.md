### D. Contributor testing instructions — **new, does not exist**

`docs/CONTRIBUTING.md` §"Development setup" gives a build command and `xcode_test_stable.sh`.
`scripts/steward_check.py` covers *format* re-verification. **Nothing tells a contributor how to
run the app against their own sessions and confirm the source actually works.** That is the gap.

What the doc has to cover, because each one has bitten someone here:

- Build and launch — and the trap that a bundle built into the `xcodebuild test` derived-data
  path launches healthy-but-invisible. Build-only derived data, or default derived data.
- Enable the source: Settings → the agent's pane; `defaultEnabled: .whenAvailable` means it is
  off until detected, so "I see nothing" is usually enablement, not a parse failure.
- The storage-root override, so he can point at a copy instead of his live store.
- What to actually check, as a list he can answer yes/no to: sessions appear; titles are right;
  transcript renders user/assistant/tool with no empty turns; timestamps sane; search finds a
  string he can see on screen; the has-commands filter matches reality; Analytics counts it;
  Copy Resume Command produces something he can paste; **Resume actually reopens the session**
  (the one thing nobody here can test for either agent).
- How to report: what to include, and the standing warning never to paste real transcripts,
  keys or private paths.

Ship it as a section in `docs/CONTRIBUTING.md` (discoverable, already linked from the PR
template) with a pointer from `docs/adding-a-session-source.md` §7. Not a new top-level file.

## 5. Decisions taken (2026-08-23)

**D1 — What ships in 5.1 with #60 open.** The dividing line is *behaviour and claims* versus
*test coverage*, not severity.

> **All 9 remaining behaviour-or-claims items close before 5.1. The 2 test-coverage gaps ride
> to 5.1.1.**

#60 holds **19 checkboxes: 7 closed, 12 open.** Of the 12 — 9 behaviour-or-claims, 2 test
coverage, 1 contributor-only.

Closing before 5.1 (9): `main_chain_id` NULL check, `content` parts-array, the eventCount
estimate, `lightweightCommands`, `canCopyResumeCommand` purity, the dead `code.devin.com` URL,
the `.db`-validator contradiction, the "directory-scoped `--continue`" wording, and the probe
script's real-transcript printing.
Deferred to 5.1.1 (2): the malformed-payload parser test and `DevinCLIEnvironmentTests`.

Two of these were nearly deferred and should not be. The **probe-script privacy leak** is the
highest-priority item in the whole queue, above two of the blockers — the matrix lists that
script under `evidence_tools`, so we are asking volunteers to run it and paste the output into a
public issue, and it prints real prompt text. And the **dead URL** is a one-line change on a
button users click; shipping a broken link into a headline release is indefensible at any cost
ratio.

The `.db`-validator contradiction resolves the cheap way: correct the pane text and the matrix
to say *directory*, leaving the validator and discovery as they are. Discovery being more
lenient than the documented contract is fine; documentation contradicting the validator is not.

**D2 — REVISED 2026-08-23: stewards own verification *and* promo captures. The maintainer
installs no further harnesses.**

The first version of this decision had us generating screenshots from fixtures, and a second
version had the maintainer installing fx himself (it is open source and `fx login codex` runs on
an existing ChatGPT subscription at no new cost). Both are rejected. The maintainer cannot run
fifteen agents; that constraint is the entire reason the steward program exists, and solving a
promo problem by violating it would undermine the program to save one screenshot.

So: **the steward for an agent is the person who produces its screenshot**, alongside the format
check and the end-to-end resume run. All three need the same thing — someone with the agent
actually installed and authenticated.

Two consequences that follow, and neither is optional:

**(a) This is a scope change to the steward role, and the docs must say so.** STEWARDS.md today
promises a 10-minute job — "Runs one command against their own sessions" — under "What a steward
does *not* do". A promo screenshot is not that. Folding it in silently is a bait-and-switch on
volunteers. It has to appear as an **optional, credited extra**, clearly declinable, never as a
duty.

**(b) It collides with a privacy promise we have already made.** STEWARDS.md says "No sharing of
real transcripts. The check tool redacts before anything leaves your Mac." A screenshot of the
session window *is* real transcript content, unredacted, published. That contradiction has to be
resolved in the text, not papered over: the screenshot ask is a separate, explicit, opt-in
request where the steward chooses what is on screen, and nothing is published without their
say-so. The format check keeps its redaction guarantee untouched.

**Standing risk this creates.** There are **zero stewards today** — eleven `steward wanted` rows
and no volunteers since launch. Making promo material a steward deliverable means 5.1's visual
story depends on @thedavidweng accepting stewardship for both new agents (see D3). If he
declines, both agents ship best-effort with no session capture.

**Fallback that keeps the release un-hostage:** 5.1 does not strictly need a per-agent capture.
The existing hero shot shows the unified list, and "two new agents" can be carried by the badge
row and the agent legend rather than two full session screenshots. Decide the copy that way
first, and treat any steward capture as an upgrade rather than a dependency.

**D3 — Both stewardships to him, if he wants them.** Concentration is the lesser risk. Eleven
rows have read `steward wanted` since the program launched and have produced no volunteers, so
holding Devin open for a hypothetical someone else trades a real steward for a vacant slot. The
program is already built for lapses: no deadline, no response obligation, and an agent falls
back to best-effort automatically. Keep the stewards-wanted invitation open for the other
agents.

**D3 is now load-bearing.** Under the revised D2 it is not just a credit line — it is the only
route to a verification date, an end-to-end resume result, or a session capture for either new
agent. He is the sole candidate for both. Ask plainly, make all three parts individually
declinable, and design the release so a "no" costs nothing but imagery.

**D4 — Durable-bytes fix goes in-house if he has not pushed by 2026-08-26.** Three days. It is
silent data loss, the 27-file conflict surface grows every time main moves, and we have already
merged one PR with findings open — doing it twice would make it the house style rather than the
exception. Same deadline applies per-fix: if he pushes the wording correction but not the
decode helper, we write the decode helper. We merge *with* the fix, never around it.
