## Task 1 (Tier A): make `QWEN_HOME` fall back to `~/.qwen`

### The bug

Johannes established that **0.22.3 reads `QWEN_HOME` via `getGlobalQwenDir()`, and 0.14.3 does
not** — 0.14.3 goes straight to `~/.qwen`. `QWEN_RUNTIME_DIR` separately overrides the
runtime-output location and is process-local, so it stays a manual override; do not try to
auto-detect it.

Both of our resolvers treat `QWEN_HOME` as authoritative with no fallback:

- `AgentSessions/Services/QwenSessionDiscovery.swift` → `sessionsRoot()`
- `AgentSessions/Qwen/QwenSourceDescriptor.swift` → the `projectsRoot` closure

So a user on Qwen **0.14.x** who has `QWEN_HOME` exported for any unrelated reason has their
sessions in `~/.qwen/projects` while we look only in `$QWEN_HOME/projects`. They see **zero Qwen
sessions** and reasonably conclude support is broken. This is the classic zero-rows false bug
report.

### What to change

When **`$QWEN_HOME/projects` is not an existing directory**, fall back to `~/.qwen/projects`.

The trigger is a single `directoryExists` check, deliberately **not** "the root contains no
discoverable sessions". An enumeration-based trigger cannot be shared: the descriptor's
`projectsRoot` closure feeds `isAvailable` (`QwenSourceDescriptor.swift:45`), which is a cheap
path test, and putting a directory walk there hot-paths the availability context. Since the two
resolvers must agree (below), the trigger has to be something both can afford.

Constraints:

- If `$QWEN_HOME/projects` exists, it wins — a 0.22.x user must be unaffected.
- An explicit user override (`QwenPreferencesKey.sessionsRootOverride` / `customRoot`) must
  **keep winning over both**. Someone who set a path by hand meant it; do not silently redirect.
- **The `QWEN_HOME` branch requires a `projects` subdirectory; the `customRoot` branch keeps
  `normalizedProjectsRoot`'s `<root>`-itself acceptance.** This is a deliberate narrowing, not
  an oversight. `getGlobalQwenDir()` makes `QWEN_HOME` the `.qwen` equivalent, so sessions live
  at `$QWEN_HOME/projects` by the CLI's own semantics; requiring it is closer to the writer than
  today's behaviour. An explicit hand-set path is a different promise and keeps both shapes.
  Without this split the fix does not fire at all for the very user it targets — their
  `$QWEN_HOME/projects` is absent, so `normalizedProjectsRoot` returns `$QWEN_HOME` itself,
  which exists, and nothing falls back.
- **Accepted limitation, to be pinned by a test rather than discovered later:** `QWEN_HOME` set,
  `$QWEN_HOME/projects` present but holding no sessions, `~/.qwen/projects` holding sessions →
  the primary still wins and the user sees zero rows. Only an enumeration trigger would catch
  it, and a 0.22.x user with a real-but-empty projects dir should not silently be shown their
  old 0.14.x sessions anyway.
- Both resolvers must agree. If discovery falls back and the descriptor does not, availability
  and indexing will disagree about whether the source exists.

### Tests to add (`AgentSessionsTests/QwenIntegrationTests.swift`)

Use a temp `homeDirectory` and an injected `environment` — both are already constructor
parameters on `QwenSessionDiscovery`, so no new seams are needed.

1. `QWEN_HOME` set to a dir with **no `projects` subdirectory** (the described user), sessions
   present in `~/.qwen/projects` → sessions are found. **This test must fail before the
   change** — verify that, or you have not tested the fix. Note it fails for the right reason
   only if the dir exists but lacks `projects`; a wholly nonexistent `QWEN_HOME` is a weaker
   case that some implementations would pass by accident.
2. `QWEN_HOME` set to a dir that *does* contain `projects/` with sessions → those win, `~/.qwen`
   is not consulted.
3. Explicit `customRoot` set, `QWEN_HOME` also set → `customRoot` wins.
4. Explicit `customRoot` pointing directly at a projects dir with **no nested `projects/`** →
   still resolves, pinning that the narrowing in the previous section did not leak into the
   `customRoot` branch.
5. `QWEN_HOME/projects` exists but is empty, `~/.qwen/projects` has sessions → **zero sessions**.
   This pins the accepted limitation as a decision; if someone later "fixes" it they will have
   to delete an explicit test and read why it was there.
6. Neither set → unchanged `~/.qwen/projects` behaviour.

The same matrix must be asserted against `QwenSourceDescriptor`'s `projectsRoot` closure, not
only against `QwenSessionDiscovery`. A discovery-only test suite is exactly how the two
resolvers drift apart.

Existing fixtures live in `Resources/Fixtures/stage0/agents/qwen/`. `QwenIntegrationTests`
asserts **exact event counts** on the existing fixture files — do not edit them. If you need new
input, add a new file, which is the convention that was already followed when
`system_telemetry.jsonl` was added for this reason.

## Task 2 (Tier B): classify the new subtypes explicitly

Top-level `type` is still `user | assistant | tool_result | system`. These `subtype` values
exist in the 0.22.3 source and did not exist in 0.14.3.

### The top-level `type` decides whether this task does anything at all

Read this before the table. The bucket a subtype "should" land in is not the interesting
question — **which top-level `type` carries it** is, because the parser already treats the two
branches completely differently:

- **`type == "system"` → already meta, unconditionally.** `QwenSessionParser.swift:452` emits
  every system record as `.meta` with `role: subtype` and `rawJSON` intact, recognised subtype
  or not. For a system-typed subtype, "classify as meta" is **already true today**, and writing
  code to say so changes nothing. The only way to alter a system record's fate is to add it to
  `artifactSubtypes` — which is the one edit this task forbids (see the topology rule below).
- **`type == "user"` → renders as conversation.** `QwenSessionParser.swift:385` falls through to
  `.user` for any subtype not in `runtimeUserSubtypes`, and `:179` lets that same record become
  `firstUserTitle`. This is the real "bookkeeping rendered as conversation" failure, and it can
  put a metadata blob in the session list as the session's title. `runtimeUserSubtypes` is the
  correct seam: one `Set<String>`, non-destructive, and already excluded from title derivation.

The source diff told us these strings exist; it did not tell us which `type` writes them.
**Determine the `type` per subtype from the 0.22.3 source before writing any code.** Where it
cannot be established, treat the subtype as system-typed — which means doing nothing, the
correct default under the governing rule.

Consequence worth stating plainly: if all thirteen turn out to be system-typed, the correct
deliverable for Task 2 is **documentation and no code change**. That is a success, not a
shortfall. Do not manufacture a diff to prove the task was done.

The two columns are sequenced, not parallel. **`type` is the gate; bucket confidence is what you
consult after the gate opens.** A system-typed row is a no-op no matter how the bucket is rated,
so its confidence never gets used. A user-typed row is where the bucket rating becomes the actual
decision: it is what determines whether the subtype earns a place in `runtimeUserSubtypes`. Read
the type column first and stop there if it says `system`.

**RESOLVED from the 0.22.3 writer** — every row below is now read from
`createBaseRecord(...)` at the actual write site in `chunks/chunk-PZ66FRIC.js`. No inference
remains, so the confidence column is retired.

| Top-level `type` | subtypes | What we do |
|---|---|---|
| `system` | `branch_checkpoint`, `goal_state`, `rewind`, `parent_session`, `session_source`, `session_model`, `file_history_snapshot`, `turn_result`, `slash_command`, `chat_compression`, `ui_telemetry`, `at_command`, `attribution_snapshot`, `custom_title`, `user_text_elements` | nothing — `:452` already renders every system record as meta with raw JSON |
| `user` | `goal_runtime`, `cron`, `notification`, **`mid_turn_user_message`** | first three already in `runtimeUserSubtypes`; the fourth is real user text and correctly renders as conversation |
| `user` **or** `assistant` (the entry's own role) | **`realtime_message`** | nothing — it carries real message content and already renders as conversation |

**The outcome Task 2 allowed for: no code change.** Everything system-typed was already meta;
the two user-typed newcomers already render correctly.

**Two inferences in the original table were wrong, both in the dangerous direction.**
`realtime_message` is written by `recordRealtimeConversation` as
`{...createBaseRecord(entry.role), subtype: "realtime_message", message: <real text>}` — bucketing
it to meta would have hidden actual conversation. `mid_turn_user_message` is likewise a real user
message with `systemPayload.displayText`. The "do not bucket on inference alone" rule added above
is what stopped both.

**The list was 13; it is 22.** Missing from the original: `chat_compression`, `slash_command`,
`ui_telemetry`, `at_command`, `attribution_snapshot`, `mid_turn_user_message`, `agent_bootstrap`,
`agent_launch_prompt`, `agent_retry`. Separately, 0.22.3 **writes** `user_text_elements` but omits
it from its own `KNOWN_RECORD_SUBTYPES`, so upstream's validator flags records upstream itself
writes. Ours includes it deliberately.

The two verified rows are the pattern to match: one system-typed subtype handled by a targeted
read at `:208`, three user-typed subtypes handled by membership in `runtimeUserSubtypes`. Nothing
else in the parser branches on subtype.

**`realtime_message` is the one row where "default to meta" is not the conservative choice.**
Everywhere else, meta is the safe direction — a metadata record shown as meta is correct, and a
metadata record shown as conversation is merely ugly. Here the error runs the other way: if it is
user-typed *and* user-visible, putting it in `runtimeUserSubtypes` demotes a real message out of
the conversation view and out of title derivation (`:179`). That still satisfies the governing
rule — the record is present as meta with `rawJSON` intact, nothing dropped or re-parented — but
it is the one classification whose failure mode a reader would experience as a missing message.
Given a `guess`-grade bucket, do **not** add it to `runtimeUserSubtypes` on inference alone. If
the source says user-typed, leave it rendering as conversation until a real transcript settles
it: an extra visible record is the recoverable error, an absent one is not.

Rules for this task:

- Every row marked inferred or guess must carry a **source comment naming this brief and
  discussion #10579** as its provenance, in the same spirit as the existing
  "read from the installed 0.21.13 package source" comment in `QwenSessionDiscovery`.
- Bucketing into meta must be **non-destructive**: the record stays in the transcript as a meta
  event with its `rawJSON` intact, exactly as `runtimeUserSubtypes` records do today. Never drop
  a record because we do not recognise it.
- **The topology rule, stated exactly: do not add anything to `artifactSubtypes`.** The chain
  walk does not consult `subtype` at all except through `isArtifact`
  (`type == "system" && artifactSubtypes.contains(subtype)`). `artifactSubtypes` membership
  removes a record from `conversationRecords`, and the active leaf is
  `conversationRecords.last?.uuid` (`:141`) — so adding a subtype there can silently move the
  leaf and re-cut the whole reconstructed chain. Everything else in this task is display-only
  and cannot reach the walk. `rewind` and `branch_checkpoint` are the tempting cases precisely
  because they sound structural; classify them for display and leave `artifactSubtypes` alone.

## Task 3 (Tier B): capture the subagent/fork fields, do not re-thread on them

**RESOLVED: four of the five fields never appear in the files we parse.** 0.22.3 writes subagent
transcripts through a *separate* writer to
`<projectDir>/subagents/<sessionId>/agent-<agentId>.jsonl`, with its own file descriptor, its own
`lastUuid` chain, and `isSidechain: true` stamped on every record (`getSubagentsRootDir` /
`getAgentJsonlPath`). `agentId`, `agentName`, `agentColor`, `isSidechain`, `agentRunId` and
`agentRound` exist only there.

`QwenSessionDiscovery.transcriptLocation` accepts only `<project>/chats/<id>.jsonl` and
`chats/archive/<id>.jsonl`, so we never read those files — and `agent-<agentId>.jsonl` would fail
the session-ID filename predicate anyway. **The interleaving risk this task was written to avoid
does not exist**, and there is nothing to re-thread.

Only `forkedFrom: { sessionId, messageUuid }` appears in `chats/` transcripts (stamped at fork).
It is already retained verbatim in each event's `rawJSON`, which is what "capture and surface"
asked for; `testForkedFromIsRetainedOnTheRecordItWasWrittenOn` pins it. **No code change.**

Consequence worth recording separately: subagent runs are entirely invisible to Agent Sessions
today. That matches `agent-support-matrix.yml`, which already lists "subagent hierarchy" under
`unsupported_surfaces` for Qwen. Supporting it is a new feature, not part of this brief.

Original (pre-source) framing, kept for context — new optional fields: `agentId`, `agentName`,
`isSidechain`, `agentRunId`, `forkedFrom`.

**Do:** parse and retain them on the record, and surface them where a reader can see them
(metadata/raw JSON). This is pure capture and cannot regress a 0.14.3 session, which simply
never carries the keys.

**Do not:** change how the transcript threads based on them — yet. We render subagent trees for
other agents, and if Qwen writes sidechain records into the same JSONL, our `uuid`/`parentUuid`
chain could interleave subagent turns into the main conversation. **We do not know whether they
are in the same file.** Re-threading on a guess degrades transcripts silently, which is worse
than showing an extra record.

The one conservative exception, if and only if it can be done without touching the chain walk:
where `isSidechain == true`, mark the event so the UI *could* distinguish it later. Marking is
fine; re-parenting is not.

## Task 4: make unknown subtypes visible instead of silently absorbed

**IMPLEMENTED.** `QwenSessionParser.unrecognizedRecordCensus(at:)` counts records keyed by unknown
top-level `type`, or `"<type>/<subtype>"` when the type is known and the subtype is not, checked
against 0.22.3's `KNOWN_RECORD_SUBTYPES` mirrored into the parser. When a transcript contains any,
one trailing meta event reports them. A 0.14.3 transcript produces none, so no existing event
count moved.

Deliberately unchanged: unknown-type records still stay out of the chain walk. 0.22.3's own
`validateTranscriptRecord` skips them too, so keeping that identical preserves leaf selection;
the census makes the omission visible rather than silent.

Also confirmed while reading the monitoring config: `agent-watch-config.json` already sweeps both
`$QWEN_HOME/projects` and `~/.qwen/projects` with `**/*.jsonl`. The Python side had the Task 1
fallback all along — the app was the half that disagreed — and that glob would pick up
`subagents/**/agent-*.jsonl` if one ever appeared.

This is the highest-value item in the brief, because it is what converts the next real
transcript into knowledge automatically.

Add a way to surface `type`/`subtype` combinations the parser does not recognise — a counter, a
diagnostic, or whatever fits existing patterns in the monitoring tooling (see
`scripts/agent_watch.py` and `scripts/rebuild_stage0_baseline.py`, which already reason about
unknown types and keys per agent). The goal: when someone finally opens a 0.22.x session, we
learn what is actually in it rather than absorbing it into a catch-all and never finding out.

**The case is stronger than "absorbed into a catch-all": unknown top-level types are dropped
outright.** `validatedRecord` (`QwenSessionParser.swift:278`) gates on
`validRecordTypes.contains(type)` and returns `nil` otherwise, so a record carrying a `type`
Qwen adds after 0.14.3 never becomes a `Record` at all — it does not reach a catch-all, it
leaves no trace, and the session parses as though it were never written. Unknown *subtypes* are
merely mis-bucketed; unknown *types* vanish. Instrument that guard, not only the subtype branch.
It is also the one place where a 0.22.x transcript could silently lose content rather than
merely mislabel it, which makes it the only part of this brief that can actually damage a
transcript.

## Fixtures for Tasks 2–3

New fixtures must go in a **new file** under `Resources/Fixtures/stage0/agents/qwen/`.
`QwenIntegrationTests` asserts exact event counts on every existing fixture; appending to one
breaks tests. This is why `system_telemetry.jsonl` was added as its own file.

**Label them synthetic, in the file and in the test name.** These records are modelled from a
source diff, not captured from a real CLI. The 5.0 incident happened because synthetic fixtures
were mistaken for coverage of a real surface. They are legitimate as parser exercises; they are
not evidence about the format.
