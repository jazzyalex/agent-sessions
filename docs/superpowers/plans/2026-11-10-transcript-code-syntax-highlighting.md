# Transcript Code Syntax Highlighting — Implementation Plan

November 10, 2026

## Goal and scope

Make code easier to scan in Agent Sessions. Apply a shared syntax palette to fenced code blocks in Session messages and identifiable code in expanded tool output. Use the November 7 Swift excerpt as the first visual fixture on both surfaces.

The scope is syntax foreground color. Diff rendering is complete. Tutor is a separate feature. Commands, generic tool input fields, the Show Script pane, inline code chips, and transcript status indicators are outside this plan.

The owner's November 10 screenshot extends expanded-tool coverage to interpreter-identified heredoc bodies and source spans in recognized `git blame` output. Heredoc language comes from Python, shell, or Node interpreter syntax. Blame reads must name the same literal source path, even when different paths would select the same language; default blame rows do not identify file boundaries. Validate the full command: reject multiline commands unless the later lines form one complete final interpreter heredoc, with no executable suffix. The only other eligible command segments are `git log` and a final recognized interpreter heredoc; cwd changes, wrapped blame calls, and other unrecognized commands force plain output. Existing paired-result, exit-status, truncation, and Codex singleton checks still apply before an output hint is built. Only source spans receive the language hint. Evidence: `ToolOutputSyntax.blameRead` in `AgentSessions/ToolRendering/ToolOutputSyntax.swift`, `ToolInvocationBuilder.splitHeredoc`, and the command/file-boundary fixtures in `ToolInvocationBuilderTests` and `ToolDetailRendererTests`.

## Task 1 — Define eligible code and select a tokenizer

- [ ] **Inventory language hints in a small sample of existing sessions.** Sample message fences and expanded reads across Codex, Claude, and at least one other available source. Record the source, language hint, and output shape for each sampled case. Start the grammar evaluation with Swift, Python, JavaScript, TypeScript, shell, JSON, and YAML. Record the initial supported list and its aliases after sampling.
- [ ] **Define language selection for message fences.** Use the explicit language tag already provided by the Markdown parser and normalize known aliases. Untagged or unsupported fences and indented blocks use the plain code style.
- [ ] **Define eligibility for native file reads.** Record supported tool and argument combinations by source, starting with Claude `Read` and verified reads from another source. Require a paired result containing one file’s source and take the language hint from the structured path. If a known result format includes a wrapper, identify its exact source body in the decoded text before coloring. Titles, line numbers alone, directory results, errors, and ambiguous or unpaired payloads are insufficient evidence.
- [ ] **Recognize tagged fences in eligible output bodies.** Inspect bounded decoded text in formats that carry a Markdown or code result. Require a complete fence with a recognized language and exact UTF-16 body bounds. A Markdown shape flag, a quoted fence inside a log, or a delimiter inside a known source file is insufficient. Color the body in place so the tool pane retains its current text, including the delimiters. Give a verified source-file language precedence when the result is that file’s contents.
- [ ] **Specify the plain fallback.** Logs, mixed command output, directory listings, errors, truncated or persisted previews, images, binary placeholders, and diffs retain their plain presentation. Apply every language hint only to the matching result and action in a multi-action invocation.
- [ ] **Choose one offline tokenizer.** Compare candidates on supported grammars, license and bundle cost, thread safety, malformed and incomplete snippets, multiline state, and runtime under the limits below. Require token categories with valid UTF-16 ranges in the exact input string. Record the choice and version before adding a dependency. Prefer a small palette of keywords, literals, comments, and named symbols.
- [ ] **Pin the performance cases before integration.** Capture the current Release baseline and record acceptance targets for the Task 4 metrics before implementing either renderer. Set the first-color target from the bounded tokenizer trial and specify the measured hardware and inputs.

### Codex shell-read allowlist

- [ ] **Match the full recorded command for one action.** Accept `cat <file>`, `nl -ba <file>`, `sed -n '<range>' <file>`, and `nl -ba <file> | sed -n '<range>'`. A range is one positive line number followed by `p`, or two positive line numbers in ascending order separated by a comma and followed by `p`. The file operand must be one literal path with a supported extension or filename. Literal quoting is supported. Use structured working-directory metadata and the existing recognized shell wrapper where applicable.
- [ ] **Keep compound commands plain.** The exact `nl` to `sed` form above is the sole pipeline exception. Multiple commands or files, arbitrary pipes, redirection, expansions, globbing, substitutions, and heredocs fail eligibility. Inspect the original command or argv before display transformations such as stripping a leading `cd` or splitting a heredoc. Determine eligibility from the saved invocation and result, with no command execution or file access.
- [ ] **Require literal command arguments.** For a direct shell call, use the recorded structured command string or literal argv. For a child of Codex `exec`, validate the original JavaScript source and require a complete literal argument object with one command field. Reject spreads, computed or duplicate keys, shorthand properties, interpolation, and expressions that can change the arguments. The existing display parser can skip spreads and retain partial arguments, so its parsed fields alone cannot establish what ran.
- [ ] **Prove which result belongs to each command.** For direct shell calls, require an exact recorded call-to-result link. For `exec`, support the captured straight-through form `text(await tools.exec_command({…}))` with one complete output chunk. For a batch, require an unconditional sequence of those direct emissions in source order and recorded result boundaries that establish exactly one chunk per emission. If the record flattens those boundaries, only a provable singleton is eligible. Matching call and chunk counts through the existing positional assignment is insufficient. Stored, reordered, repeated, or unassigned results and polls fall back to plain text.
- [ ] **Compute a typed syntax hint before building `ToolAction`.** In the invocation builder, evaluate the original arguments and their proven result before calling `finish`. Require explicit exit code zero from the exact direct result or child chunk, a complete decoded source body, and no conflicting error evidence. For `nl`, require the existing decoder to recognize the numbered body. Check truncation on both the result or chunk and the enclosing `exec` before invocation facts are attached to the last child. Enclosing truncation disqualifies every child. Carry only the resulting optional per-output syntax hint into the presentation. Display status and the formatted Copy and Find text are insufficient evidence.
- [ ] **Use both positive and negative Codex fixtures.** In the November 7 session `01a1b92f-e29b-7b82-964d-86140e9652fa`, the standalone `sed -n '246,320p' AgentSessions/Utilities/CodexSessionImagePayload.swift` call and its successful result are at lines 587 and 590. Line 50 contains multi-command actions with numbered reads. Use those as positive and negative fixtures respectively. Add isolated positives for `cat`, `nl`, and the allowed `nl` to `sed` pipeline. Add a positive batch fixture if the corpus contains a recording format that proves per-emission boundaries. Add negatives for spread and computed overrides, duplicate command fields, dynamic or malformed arguments, reversed results with equal counts, unproven batch boundaries, an unassigned chunk, a missing or nonzero child exit despite script completion, chunk truncation, and enclosing truncation with an otherwise eligible earlier child. Assert that rejected cases produce plain output and no syntax hint.

## Task 3 — Color expanded tool output

- [ ] **Carry per-action code hints into expanded output.** Apply Task 1’s eligibility rules to decoded source or a tagged fence body. For Codex shell reads, consume the builder’s verified hint for that output. Preserve the decoder’s text, search ranges, and copy payload. Keep the existing off-main expanded-tool renderer. Submit tokenizer work only for visible, open output bodies. The ordinary presentation path can also run during height measurement and Find, so those paths alone must not schedule syntax work.
- [ ] **Specify the coordinate conversion.** Token ranges start in the snippet. Add the snippet’s UTF-16 start in `DecodedText.text` to get output-relative offsets. Project tokens through the visible output spans produced when appending numbered lines, folded segments, and clipped prefixes. Find uses those same spans plus `PlainLayout.output` to obtain offsets in the action’s full plain text. Keep syntax projection in decoded-output coordinates so an absent Find base does not prevent coloring. Keep gutter, fold control, link, and Copy attributes intact.
- [ ] **Preserve token state across folds.** Tokenize the entire eligible snippet within the budget, then project the result through the current output layout. Reuse tokens across width, fold, and appearance changes. Apply a result only to the matching current presentation and repaint foreground in a batch. This keeps multiline comments and strings consistent across Show More, Show All, and long-line expansion.
- [ ] **Verify Find and both Copy paths.** Extend `ToolDetailRendererTests` and the tool cell tests. Use Unicode before a token in numbered and clipped output, and compare colored and plain text, mapping, and active Find behavior. Include multiple actions so tokens and matches land on the correct one. Exercise Find reveal and clear across folds. Test native selection and menu Copy with a selection crossing a gutter or fold control, and separately verify that Copy Output returns the entire decoded body, including folded content. Check that neither Copy path submits tokenizer work on its own.

### Implementation measurements

- The sample used the first 4,000 records of each pinned Codex and Claude session and up to 400 parts from each of four recent OpenCode sessions for this repository. It found 204 Codex TypeScript tags, 71 Claude Bash tags, 58 Claude Read calls with `file_path`, and 67 OpenCode reads with `filePath` and a complete file wrapper. Use Swift, Python, JavaScript, TypeScript, shell, JSON, and YAML with the aliases in [TranscriptSyntax.swift](../../../AgentSessions/Services/TranscriptSyntax.swift).
- The tokenizer uses Foundation's ICU regular expression engine and emits UTF-16 ranges. An optimized, 15-run trial on an eight-core Apple M1 Pro measured 2.8–18.3 ms p95 across six inputs near the 50 KiB cap. This kept the syntax pass offline and within budget without another package.
- Use the 78,018,481-byte Codex and 45,457,895-byte Claude inputs from the previous gate. Their bytes match the recorded SHA-256 fingerprints. For the representative syntax fixtures on the same machine, use p95 limits of 100 ms for first color after plain display, 100 ms for cold expansion and fold to color, 50 ms for cached reopening, 25 ms per rapid-scroll step, and 16.7 ms for one main-thread color pass. Retain the 5% large-session open limit and the queue ceilings of two active and eight waiting jobs.
